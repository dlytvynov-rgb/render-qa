# Сверка — чеклист перевірки аутпута по типах документів

**Дата:** 2026-07-14
**Статус:** затверджено Димою (інтеграція + вкладка · AI перевіряє → ПМ підтверджує · автокласифікація + тег)

## Проблема

Існуючий чеклист (Q1.1–Q4.1) організований по типах дефектів. ПМ у студії працює інакше — по типах документів пакета: відкрив RCP → звірив стелю, відкрив FFE → звірив меблі. Потрібен другий шар перевірки — «Сверка» — з фіксованим студійним списком з 13 пунктів, де кожен пункт прив'язаний до типу вхідного документа.

## Реєстр пунктів — `SVERKA_CHECKS`

Нова константа в `src/App.jsx` поряд з `QA_CHECKS`:

```js
const SVERKA_CHECKS = [
  { id: "S1",  label: "Модель по референсу",     needs: ["reference"] },
  { id: "S2",  label: "Студійні стандарти",       needs: [] },            // завжди активний
  { id: "S3",  label: "FFE",                     needs: ["ffe"] },
  { id: "S4",  label: "Текст, позначки",          needs: [] },            // завжди активний
  { id: "S5",  label: "Результат до референсу",  needs: ["reference"] },
  { id: "S6",  label: "Деталі / вузли",           needs: ["detail"] },
  { id: "S7",  label: "Ландшафтний план",         needs: ["landscape"] },
  { id: "S8",  label: "Елевейшени (екстер'єр)",   needs: ["elevation"] },
  { id: "S9",  label: "План розміщення",          needs: ["floorplan"] },
  { id: "S10", label: "RCP план",                 needs: ["rcp"] },
  { id: "S11", label: "Матеріали",                needs: [] },            // завжди активний
  { id: "S12", label: "Розгортки",                needs: ["unfold"] },
  { id: "S13", label: "Ту-ду лист (правки)",      needs: ["todo"] },      // або mode === "revision"
];
```

- `needs: []` = пункт завжди активний.
- Пункт активний, якщо серед завантажених файлів є хоч один з `_docType` ∈ `needs`.
- S13 також активний у режимі «Порівняння раундів» без окремого документа.
- Дубль «перевірка деталей/вузлів» з вихідного списку злито в один S6.

## Тегування документів (`_docType`)

Кожен файл у `useFileList` отримує поле `_docType` (string | null).

**Автокласифікація** — синхронна евристика по імені файлу при додаванні (без API-викликів):

| Патерн у назві (case-insensitive) | _docType |
|---|---|
| `rcp`, `ceiling` | `rcp` |
| `elev`, `фасад`, `facade` | `elevation` |
| `ffe`, `furniture` (+ Excel у брифах) | `ffe` |
| `landscape`, `ландшафт`, `озелен` | `landscape` |
| `розгорт`, `unfold`, `wall` | `unfold` |
| `todo`, `правк`, `fix`, `comment` | `todo` |
| `plan`, `план`, `layout` | `floorplan` |
| `detail`, `вузл`, `узл`, `node` | `detail` |
| файл у зоні РЕФЕРЕНСИ | `reference` (дефолт зони) |
| інакше | `null` (не бере участі в активації) |

**Ручна корекція** — маленький `<select>` на чіпі файлу в `UploadBox`/`DwgSlot` (поряд з існуючим інпутом тега референса): список типів + «—». Значення пишеться через новий метод `updateDocType(id, type)` у `useFileList` (аналог `updateTag`).

## Промпт і схема відповіді

У `runAnalysis` (гілка first) і в revision-гілці до промпта додається блок:

```
── СВЕРКА (студійний чеклист) ──
Перевір КОЖЕН активний пункт. Прив'язка документів:
S10 RCP план → [КРЕСЛЕННЯ 2: RCP_final.pdf]
S8 Елевейшени → [КРЕСЛЕННЯ 1: south_elev.pdf]
...
Неактивні пункти (S7, S12) познач status: "no_material".
```

Список активних пунктів і прив'язок генерується з `SVERKA_CHECKS` × завантажених файлів.

У `JSON_SCHEMA` додається масив:

```json
"sverka": [{"id":"S10","status":"ok","note":"Світильники по RCP — 6/6 на місцях","doc_ref":"RCP_final.pdf","zone":{"x":40,"y":8,"w":20,"h":10}}]
```

`status`: `ok` | `warn` | `fail` | `no_material`. `zone` обов'язкова для `warn`/`fail`, опційна для `ok`.

Обробка відповіді: `sverka` проходить через `normalizeZones` (додати `sverka` у `fixArr`), зберігається в `perData[i].sverka`.

## UI — вкладка «Сверка» в DetailPage

Перша вкладка в `tabs1` (перед «Звіт»), показується завжди коли є `data`.

**Рядок пункту:** статус-іконка (✅/⚠️/❌/⬜/·) → назва → чіп документа (`doc_ref` або назва файлу з відповідним `_docType`) → note → 📍 якщо є zone (hover підсвічує маркер на рендері — той самий механізм `hovId`).

**Override ПМ:** клік по статус-іконці циклює ok → warn → fail → ok (тільки для активних пунктів зі статусом від AI; ⬜ і «не перевірено» не клікаються). Поряд з'являється бейдж «ПМ». Зберігання: `perData[i].sverkaOverrides = { S10: "fail", ... }` — мержиться при рендері поверх AI-статусів, потрапляє в `saveSession` і в PDF.

**Шапка вкладки — прогрес:** `N/13 перевірено · X ❌ · Y ⬜ без матеріалів` + тонкий прогрес-бар.

**Статуси відображення:**
- `ok`/`warn`/`fail` — від AI або override;
- `no_material` (⬜) — пункт неактивний, підказка «додай <тип> у пакет»;
- «не перевірено» (·) — реєстровий пункт, якого немає у відповіді AI (стара сесія, обрізаний JSON).

**Зони:** елементи `sverka` з zone вливаються в `allAnns` як `_src: "sverka"` з кольором по статусу — маркери на рендері та в «Креслення» працюють без змін.

## PDF

У `generateReport` нова секція «Сверка» після QA-чеків: таблиця 13 рядків — статус (з урахуванням override, бейдж «ПМ»), назва, документ, note. Стиль — існуючий (`.chk`-подібні картки).

## Fallback-и та сумісність

- Стара сесія / немає `sverka` у відповіді → вкладка рендерить реєстр зі статусом «не перевірено». Нічого не падає.
- `sverkaOverrides` відсутні → порожній об'єкт.
- Excel FFE вже парситься в текст (`excelToText`) — додаткової обробки не треба, лише тег `ffe`.

## Верифікація

- `npx vite build` + `npx eslint` без нових помилок.
- Ручний прогін: пакет з рендером + RCP + референс → у вкладці «Сверка»: S1/S2/S4/S5/S10/S11 зі статусами, решта ⬜; override клікається і переживає збереження/відновлення сесії; PDF містить секцію.

## Поза скоупом

- Окремі слоти завантаження під типи документів (відхилено — тег замість слотів).
- Haiku-класифікація файлів по вмісту (можлива ітерація 2, якщо евристика по іменах не витягне).
- Зміна старої системи Q-кодів.
